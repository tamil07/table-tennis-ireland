# Operational implementation decision

Updated 7 November 2026. This supplements `design.md` and supersedes its assumption that the original normalized schema already supplies operational workflows.

## Shared rules and authoritative service

`packages/domain/src/operations.ts` defines club-scoped commands and invariants. `packages/ui/src/ClubPortal.tsx` is reused by the website and PWA. Synthetic mode executes those rules against browser-local fake data; explicit live mode sends commands to `club-api`. The live server verifies the Auth bearer user, loads current state, checks current permissions and guardian relationships, validates the command and commits with a revision check. Frontends never submit authoritative snapshots or choose their acting identity.

For this small single-club pilot the new canonical operational data is a versioned JSON aggregate in `club_runtime`, not a second independent website inventory. It contains people, scoped grants, membership/product snapshots, manual payments, dated sessions/table allocations, requests, attendance/availability, events, matches, reflections, assessments/notes, content, work items, notifications and audit deltas. A derived `club_runtime_members` index lists a verified user's clubs without scanning every club's private state. The original relational tables and venue-QR RPCs remain legacy foundation source; the new frontends do not write those tables or use the old Attendance/SessionBookingDemo screens. Do not write the same business record to both stores.

This aggregate deliberately serializes writes within a club using compare-and-swap. It is a pilot tradeoff, not an unlimited scale claim. It simplifies atomic guardian/permission checks and tournament/booking transitions while all writes pass through one tested command service. Authenticated database clients cannot read/write the aggregate or directory directly. The privileged commit function is callable only by the server role, fixes its SQL search path, preserves the owner and checks revision plus active player/place uniqueness and the four-place range. Version conflicts return HTTP 409; the client refreshes rather than silently overwrites.

Every mutation has an actor-scoped idempotency key and optional expected version (required by the live HTTP service). Replays return current permitted state without repeating side effects. Audit uses changed rows/table allocations rather than copying all booking history on every request. Idle scheduler passes do not grow history or bump revisions. Polling uses the revision to avoid retransmitting unchanged snapshots. Before larger production use, load-test state size, payload/egress, concurrent writes and audit growth; partition/normalize the command store without changing the shared command contract when measurements justify it. No claim of nationwide production capacity is made by this pilot.

## Permissions and privacy

Permissions distinguish access management, membership, bookings, attendance, events, coaching, content, communications and privacy. Runtime grants/revocation are enforced on every command. Guardians can act only for currently linked juniors. Public projection omits people, attendance, scores/reflections, private notes and management records. Private working notes and reflections do not leak through ordinary roster responses or access-manager audit responses. Membership teams see their permitted financial history without general access to coaching content.

Independent end-user accounts use Supabase Auth email/password, verification, recovery, magic links and optional Google linking. Optional phone OTP/linking is off by default and requires explicit provider configuration. Verified phone login never implies verified email delivery. Offline-profile history is linked only through an audited authorized operation to an already verified account, with duplicate booking/tournament checks. Juniors use guardian-led applications with policy consent; managers configure public privacy/safeguarding information before accepting applications.

## Operational flows

- Membership types can be created, edited and retired at runtime. Assignments snapshot terms, dates remain manual, additional payments/corrections retain audit and acknowledgement is opt-in. Trials default to one calendar month with an inclusive end date, management extensions and end reminders.
- Sessions/camps publish dated occurrences in Ireland local time. Specific table IDs support nonconflicting concurrent allocations. Hall closures cancel affected reservations with notices and block new allocations; reopening never silently restores cancelled bookings.
- Booking uses four player places/table/full session and one active place/player/session. Holds, approval, expiry, cancellation, moves and release share the same rules. Booking is separate from attendance.
- Direct app and rotating venue-QR attendance require explicit presence confirmation during session time. QR stores hashes and expires within 90 seconds; re-scans and staff refresh are supported. Not attending is a separate response. Expired/no-membership attendance is retained with follow-up. Authorized corrections are excluded from counts.
- Singles/doubles matches support drafts, incomplete outcomes, deuce validation, same-club opposing-side review, coach resolution and five-day inaction auto-approval. External/unlisted-event results preserve player-reported provenance and never update internal standings. Duplicate fixture selection reuses the existing fixture; likely repeated manual entries require explicit confirmation/reason.
- Internal league/knockout events support guests, delegates, participant check-in, editable draft teams/seeding, configurable best-of/league points/tie-break order, byes and confirmed-result progression. Delegation is event-scoped, not general club administration.
- Participant/guardian reflections use stable coach-managed tags and private notes. Coaching summaries show reporting denominators, categories and event/date filters. Published development summaries need distinct coach and family sign-off; private coach notes remain separate.
- Club content publishes plain text and stable event links. Public JSON/RSS/calendar projections expose approved information only; RSS does not send email or publish automatically to Facebook.

## Notifications and retention

Commands queue in-app/email notices; they do not assert delivery. The protected scheduler processes end-of-day Europe/Dublin expiry, optional 10/3-day reminders, trial follow-up, booking expiry and five-day review. Recipient permissions, guardian links, renewed periods, optional-event consent and current Auth email are checked before external delivery. The Resend worker uses provider idempotency keys, leases, bounded attempts and a retry window below provider idempotency expiry. Failed/undeliverable items remain visible for manual follow-up. A server-only global daily budget caps application email attempts; Auth SMTP has separate configuration/usage and needs headroom. Missing provider secrets leave mail queued.

Operational retention remains disabled until management approves policy/contact information. The implemented scheduler removes operational attendance/booking and settled delivery records after 24 months, membership/payment data after seven years, and private notes for players who left more than twelve months ago. General/financial audit has corresponding protection; removed private notes must not survive in audit payloads. Published match history, photographs and reflections need separate purpose decisions and are not silently assigned operational retention. Backup expiry/off-site storage and restoration remain account/operations acceptance, with an encrypted-export script supplied.

## Packaging and handover

`npm run prepare:functions` copies canonical domain source into an ignored function-local directory. Generated copies are never edited or committed; `deploy:backend` regenerates them before `--use-api` deployment. Both CI and the handover run this preparation. `setup:migrations` emits a transactional SQL-Editor fallback with migration history, verified against isolated PostgreSQL. `setup:env` preserves existing private files; `setup:bootstrap` emits a non-destructive first-owner SQL script. `setup:schedule` emits private Vault/cron configuration.

The owner explicitly excludes hosted database setup, live backend testing and account-required configuration from office-laptop work. Follow `docs/PERSONAL_LAPTOP_LAUNCH.md` on the personal laptop, with fresh Supabase/Cloudflare authentication and exact HTTP/Auth origins. No personal-laptop coding-agent subscription is a prerequisite.
